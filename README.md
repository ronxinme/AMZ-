# 亚马逊每日竞品记录工具 · GitHub 免费版

不租服务器、不花一分钱的云端方案：**GitHub Actions 每天定时采集 → 数据自动存进仓库 → GitHub Pages 免费托管网页**，任何设备打开链接就能看。

网页打开第一屏就是**库存预警**：自有商品断货要处理、竞品断货是机会窗口、「仅剩 N 件」低到阈值会亮出来。往下是当天数据、历史对比、商品管理三个页签。

库存数字不再只有页面公示的那几个 —— 采集脚本内置了**加购实测探针**（跟卖家精灵同一套机制：模拟加购直到无法添加）。2026-09-25 云端实测：**28 个商品里有 17 个**因此第一次拿到了具体数字，而它们此前在亚马逊页面上只写 `In Stock`。原理、实测数据、以及「为什么有的数字只能写成『最多 N 件』」，见下文「库存是怎么抓到的」。

## 售价是怎么取的（避免踩坑）

亚马逊商品页里同一个页面会有很多价格数字：主价、划线价、**每件单价**、搭配购、推荐位、其他卖家报价……

本工具的取价优先级（从高到低）：

1. `twister-plus-buying-options-price-data` 买箱 JSON —— 只含当前选中变体的成交价
2. 加购表单里的 `customerVisiblePrice` —— 顾客实际支付价
3. 价格主区块的 `priceToPay`（价签 / 无障碍标签）
4. 全局 JSON 兜底 `priceAmount` / `displayPrice`

**关键点：绝不取裸 `a-offscreen`。** 曾经踩过的坑——页面里 `priceToPay` 的 `a-offscreen` 是空的，紧随其后的第一个非空 `a-offscreen` 其实是「每件单价」：4 件装 $37.99 会被误读成 $9.50（= 37.99 ÷ 4）。现在单价单独存到 `unitPrice`，只作参考。

若某商品当天取不到价（页面显示「Available from these sellers」没有主报价），价格记为空并在历史表里显示 `—`，不会瞎猜。


## 验证码问题（重要，如实说明）

GitHub Actions 的出口 IP 是数据中心 IP，亚马逊可能弹验证码；遇到时该商品当天标记为「验证码」，**不会造数**，第二天自动重试。想提高成功率有两个免费手段（在仓库 **Settings → Secrets and variables → Actions → New repository secret** 添加）：

| Secret 名 | 填什么 | 效果 |
|---|---|---|
| `SCRAPER_MODE` | `jina` | 走 r.jina.ai 免费通道（无需 Key），成功率更高但页面格式略有差异 |
| `SCRAPER_MODE` + `SCRAPER_KEY` | `scrapingbee` + 免费注册拿 Key（每月 1000 次免费） | 住宅代理，成功率最高；200 ASIN × 30 天约 6000 次/月，超出免费额度，适合商品数 ≤ 100 的阶段 |

## 库存是怎么抓到的（加购实测）

先说结论：**本工具现在能抓到精确库存数字**，机制跟卖家精灵库存监控是同一套。

### 卖家精灵是怎么做的

卖家精灵官方论坛写过一句原话：

> **「原理是系统模拟添加产品到购物车，直到无法添加。」**

不是 API、不是他们的数据库。就是**加购探测**：拿一个匿名会话，把商品加进购物车，数量写一个很大的数（比如 999），亚马逊会自动把它**夹到当前最大可购买量**，再读购物车里那个数量框的数——那个数就是库存。

卖家精灵官方还列出过它的失效条件，正好反过来印证了这个机制：BuyBox 拥有者变化 / 这次库存比上次多（补货退货）/ 发货类型变化（自发货转 FBA）/ 限购商品 / 库存大于 999。

### 卖家精灵是怎么区分「限购」和「实际库存」的

它库存那一栏里会出现一个 `L` 标记，很多人以为是 `Low Stock`（低库存），其实不是。官方论坛的英文回复原文：

> **The "L" in Seller Sprite's stock level display specifically stands for "Purchase Limit", not "Low Stock."**
> **Data Source: Derived from Amazon's `maxOrderQuantity` API parameter.**
> **Priority Logic: Overrides actual stock calculations when active.**

翻译过来是三句话：

1. `L` = **Purchase Limit（单笔限购）**，跟低库存没关系。
2. 数据来源是亚马逊的 **`maxOrderQuantity`** 参数。
3. 一旦判定是限购，它会**覆盖**掉真实库存的计算结果 —— 也就是说它宁可显示「限购」，也不把限购数当成库存数报给你。

**对我们最有用的是第 3 条**：专业工具的做法也是**不把限购数当库存**。本工具跟着这条原则走。

麻烦的地方在于：`maxOrderQuantity` **只存在于亚马逊的 API 响应里，静态 HTML 里没有**。商品页里只有一堆空模板占位：

```html
<div id="tp-bbm-info-message-quantity-restriction-container"></div>
<div id="QuantityLimitMessage_feature_div"></div>
<div id="quantityLimitExhaustionAOD_feature_div"></div>
```

`${maxQuantity}` 变量没被填充，所以拿不到明写的限购值。既然读不到原始参数，就换一条**可观测的代理信号**来反推 —— 见下一节。

### 本工具的探针链路（四步）

采集脚本 `scripts/collect.mjs` 里的 `probeStock()` 完整复刻了这套机制：

| 步骤 | 动作 | 为什么必须这么做 |
|---|---|---|
| 1 | `GET https://www.amazon.com/` 预热会话，拿 Cookie 和 `anti-csrftoken-a2z` | 匿名裸请求会被判定为机器人 |
| 2 | `POST /gp/delivery/ajax/address-change.html` 设美国收货邮编（默认 `10001`） | **最关键的一步**。「不发中国」的商品在中文收货地址下亚马逊根本不展示买箱，加购表单里 `asin` / `offerListingId` / `quantity` 全缺失 |
| 3 | `GET /dp/{ASIN}` 抓商品页，解析真实的 `form#addToCart` 字段 | 字段必须**原样**用页面给的，自己猜一定失败 |
| 4 | `POST /cart/add-to-cart/ref=dp_start-bbf_1_glance`（quantity=999）→ **再单独 `GET /gp/cart/view.html`** → 读 `input[name="quantityBox"]` | POST 响应里**没有** quantityBox，必须再 GET 一次购物车页；读到 POST 就去找的人会误判成「加购失败」 |
| 5 | `POST /cart/ref=ord_cart_shr?...` 带上 `submit.delete-active.{itemID}` 删掉条目 | 必须带 `anti-csrftoken-a2z`，否则静默失败、条目累积、**污染后面每个商品读到的数字** |

### 实测交叉验证

**第一组：页面本来就公示了数字的商品 —— 探针结果与页面完全一致，证明探针读的就是那个数**

| ASIN | 亚马逊页面公示 | 探针结果 | 判定 |
|---|---|---|---|
| B0C743SY46 | Only 17 left | **17** | ✅ 一致 |
| B0CBKGVZSW | Only 4 left | **4** | ✅ 一致 |
| B0CJ6HD4R1 | Only 12 left | **12** | ✅ 一致 |
| B0CJ8MH322 | Only 12 left | **12** | ✅ 一致 |

**第二组：页面只写 `In Stock` 的商品 —— 页面不肯给数字，探针给出了**

| ASIN | 亚马逊页面公示 | 探针结果 |
|---|---|---|
| B09PTH84M7 | In Stock（无数字） | 夹到 100 |
| B08FB3FLF2 | In Stock（无数字） | 夹到 25 |

100 这个数用 `PROBE_QTY=200` 和 `999` 各跑一次都得到同样的结果，说明它稳定、不是取值的产物。

**第三组：云端真实跑一遍（2026-09-25，28 个商品）**

| 结果 | 数量 | 说明 |
|---|---|---|
| 加购实测拿到数字 | **17** | 这些商品此前页面只写 `In Stock`，完全看不到数量 |
| 页面自己就写了数字/状态 | 11 | 不需要探针（`Only N left` / 缺货 / 无主报价） |
| 购物车页被验证码拦 | 3 | 退回页面口径的状态值，**不造数**；已加入自动重试 |

结论：**GitHub Actions 的数据中心 IP 完全跑得通探针**（这是最担心的一点，实测证明没问题）。28 个商品里有 17 个因此第一次有了具体库存数。

### 怎么区分「限购」和「实际库存」（关键洞察）

这是整套机制里最容易误解的一点，必须讲清楚。

探针拿到的是**「亚马逊允许你一次买多少件」**。它可能来自两个完全不同的原因：

- **库存不够了** → 只剩 N 件，所以最多只能买 N 件
- **单笔限购 N 件** → 库存还有一大堆，但亚马逊不让你一次买超过 N 件

**怎么分辨？靠亚马逊在加购响应里自己说的那句话。**

#### 核心证据：亚马逊会明说「可售 N 件」还是「限购 N 件」

当请求的数量超过上限时，亚马逊会在**加购响应**里回一句话。这句话有两种形态，直接决定定性：

| 亚马逊的原话 | 含义 | 判定 |
|---|---|---|
| `You've requested more of ... than the **2 available from the seller** you've selected.` | 这个卖家只有 N 件可售 | **库存 N 件** |
| `... **limit of 100 per customer** ...` | 单笔只能买 N 件 | **限购 N 件** |

**决定性对照实证**（2026-09-26 实测）：

| ASIN | 页面公示 | 数量下拉 | 亚马逊加购响应原话 | 我们记录 | 判定 |
|---|---|---|---|---|---|
| B0C743SY46 | **Only 17 left** | 1…17 | `than the 17 available from the seller` | 17 | ✅ 库存 17 |
| B08FB3987P | In Stock | 1…30 | `than the 179 available from the seller` | 179 | ✅ 库存 179 |
| B0DR8RDRFM | In Stock | 1…30 | `than the 44 available from the seller` | 44 | ✅ 库存 44 |
| **B0HHXD8SHF** | In Stock | 1…**2** | `than the 2 available from the seller` | **2** | ✅ **库存 2** |
| **B0HFWLCSCS** | In Stock | 1…**2** | `than the 2 available from the seller` | **2** | ✅ **库存 2** |
| **B09PTH84M7** | In Stock | 1…**100** | `limit of 100 per customer` | **100** | ✅ **限购 100** |

**第一行是最硬的交叉验证**：B0C743SY46 我们读到 17，而它商品页自己就写着 `Only 17 left in stock` —— 两处数字完全吻合，**证明「the N available from the seller」说的确实是库存**。

**最后一行是限购的样板**：同样是「请求 999 只让买 100」，但亚马逊的原话是 `limit of 100 per customer` —— 这是限购，不是库存。

#### ⚠️ 一个被实测推翻的旧方案（留作教训）

这个项目早期版本做过一条**推断**：

```
夹紧值 N ≤ 20  且  商品页与购物车都没有「Only N left」文案  ⇒  判为「单笔限购」
```

推理看起来还挺硬：亚马逊对低库存商品会打印 `Only N left in stock`（实测 4 / 12 / **17** 件都有，21 件起消失），既然没打印，那 N 就不是库存。

**这条推断是错的，而且错得很贵。** 用户拿真实商品打脸了：

> B0HHXD8SHF 这家店的库存**确实只有 2**，你的工具却报「限购」—— 这是一个错误。

补做取证后发现，亚马逊在加购响应里**原话写着** `than the 2 available from the seller you've selected` —— 它有话直说，只是那句话**不在商品页 HTML 里**（藏在加购响应的 `<script>` JSON 里），所以光看页面看不出来。

**教训**：`Only N left` **有**说明库存低；但它**没有**并不能反过来证明库存高 —— 这个「缺失即否定」的推理不成立。**亚马逊有时就是不给 low-stock 文案**（B0HHXD8SHF 库存 2 件，商品页一个字都没写）。

#### 现在的规则：只信亚马逊自己说的话，一个字都不推

| 优先级 | 依据 | 判定 | 前端显示 |
|---|---|---|---|
| ① | 购物车条目里亚马逊写了 `Only N left in stock` | 库存 N | `仅剩 N 件`（蓝 + 加购实测） |
| ② | 加购响应原话 `the N available from the seller` | **库存 N** | `库存 N 件`（蓝 + 加购实测） |
| ③ | 加购响应 / 购物车 / 商品页原话 `limit N per customer` | **限购 N** | `限购 N`（红） |
| ④ | 请求 999 件被**完整接受** | 库存 ≥ 999 | `≥ 999 件` |
| ⑤ | 商品页自己写了 `Only N left` | 库存 N | `仅剩 N 件`（绿，页面原话） |
| ⑥ | 以上都没有，只有夹紧值 N | 只敢说「一次最多能买 N 件」 | `最多 N 件`（蓝） |

**为什么第 ⑥ 档必须保守？** 因为那时候亚马逊**什么说明文字都没给**（既没写低库存，也没写限购），无法确定 N 是库存还是单笔上限。所以只说上限、不断言库存 —— 宁可少说，也不冤枉商品。

**「推断」这个口径已经从代码里彻底删除**，页面上再也不会出现「限购 N（推断）」。现在的每一个「限购」，都有亚马逊的原话撑腰。

#### 五种口径，一个都不含糊

| 情况 | 探针读到 | 真实含义 | 网页显示 |
|---|---|---|---|
| 亚马逊购物车条目里写了 `Only N left in stock` | N | **就是库存**（亚马逊自己说的） | `仅剩 N 件`（蓝 + 加购实测） |
| 加购响应原话 `the N available from the seller` | N | **就是库存**（亚马逊自己说的） | `库存 N 件`（蓝 + 加购实测） |
| 亚马逊写了 `limit N per customer` | N | 限购数，**不是库存** | `限购 N`（红） |
| 请求 999 件被**完整接受** | 999 | 库存 ≥ 999 | `≥ 999 件` |
| 只把数量夹到 N，什么文案都没写 | N | 一次最多买 N 件，说不清是库存还是限购 | `最多 N 件` |

**只有当亚马逊自己说出「available from the seller」时，网页才会写「库存 N 件」。** 只说「最多 N 件」的那些，是亚马逊这次确实没给任何说明 —— 老实标着，不猜。

悬浮上去能看到亚马逊当天的原话，包括那句完整的 `You've requested more of ... than the N available from the seller you've selected.`

### 探针的局限（如实说明）

- **一次性数量上限**：购物车数量框 `maxlength=3`，最多只能写 999。库存超过 999 的只能记 `≥ 999`。
- **夹紧值 ≠ 库存**：见上一节。标 `最多 N 件` 的，就是亚马逊没给说明文字的那一档。
- **依赖亚马逊那句话**：判定的前提是亚马逊愿意在加购响应里说明原因。它要是沉默，我们就只能保守地记 `最多 N 件`（不会瞎猜成库存，也不会瞎猜成限购）。
- **限购商品**：读到的是限购数，标成 `限购 N`，绝不冒充库存。
- **跳过无买箱的商品**：`unavailable`（缺货）/ `no_offer`（无主报价）没有买箱，探针做不了，直接记状态。
- **不重复付出成本**：页面已经写明 `Only N left` 的商品不再跑探针 —— 数字已经有了，没必要多花两个请求。
- **偶发验证码，两道重试**：读购物车那一步偶尔会被验证码拦（实测云端每轮 3-4 个 / 28 个）。处理方式有两层：① 当场**重建会话重试一次**；② 主循环跑完后，把还没取到的商品**攒起来做一轮收尾补采**（换指纹再试）。两道都过不了才退回页面口径的状态值 —— 全程**不造数**。实测被拦的商品每轮都不一样，说明是会话级别的随机拦截，不是商品本身的问题。
- **必须设美国邮编**：不设的话，「不发中国」的商品亚马逊不展示买箱，探针直接做不了（实测 3/6 失败 → 设置后 0/6）。

### 前端怎么显示

库存格按**数据来源**和**口径可信度**分开显示，绝不混：

| 显示 | 来源 | 含义 |
|---|---|---|
| `仅剩 17 件` + `（亚马逊页面原话）` | 亚马逊页面 | 最可信，就是库存 |
| `仅剩 12 件` + 加购实测角标 | 购物车条目里亚马逊原话 | 同上，就是从购物车读到的 |
| `库存 2 件` + 加购实测角标 | 加购响应原话「the N available from the seller」 | 亚马逊自己说出的卖家可售数量 |
| `≥ 999 件` + 加购实测角标 | 加购 999 被完整接受 | 只能确定下界 |
| `最多 44 件` + 加购实测角标 | 被夹紧，亚马逊没给说明文字 | 一次最多能买 44 件，说不清是库存还是限购 |
| `限购 100`（红） | 亚马逊限购文案 | 亚马逊明写的限购数，**不是库存** |
| `有货` / `缺货` / `无主报价` | 亚马逊页面状态 | 没有数字 |

- **蓝色 = 加购实测**，绿色 = 亚马逊页面原话，**红色 = 限购（是购买数量上限，不是库存）** —— 颜色跟下方图例对应，一眼能分。
- **悬浮任意库存格**能看到完整依据：亚马逊原话、探针怎么夹的、为什么标「最多」、限购文案写在哪一处（商品页 / 购物车 / 加购响应）、当天有没有被验证码拦、买箱是否指向变体子 ASIN。
- 历史对比页每天的库存格同样按这套口径区分，悬浮看当天的说明。

### 除了库存，这些免费信号也值得看

- `Only N left in stock - order soon.` —— 亚马逊**主动**显示的仅剩数量，只在库存偏低（约 20 件以内）时才出现

## 库存预警面板（网页顶部，全站可见）

打开网页第一眼就能看到的那条彩条，就是库存预警。它把当天所有商品的库存状态自动归成三档：

| 分组 | 什么会进来 | 该做什么 |
|---|---|---|
| 🔴 **自有商品·需处理** | 你自己的商品**断货**、**无主报价**，或数字小到阈值以下（`仅剩 N 件` / `最多 N 件` / **`限购 N`**） | 立刻处理（补货 / 查 listing 是否被抑制） |
| 🟠 **竞品·机会窗口** | 竞品**断货**、**无主报价**，或数字小到阈值以下（含**限购**） | 抢排名 / 广告加码的时机 |
| ⚪ **其他精确数量** | 拿到了精确数字但数值还大的（含大额限购） | 仅供参考 |

**限购为什么也进前两组**：自家商品被限制「单笔只能买 1 件」是要处理的事；竞品被限购，就是你抢单的窗口。两者都比「最多 41 件」更该被看见，所以不会掉进「其他」里。分流规则跟库存一致 —— **数字小 = 越该看**，阈值用右上角那个「低库存阈值」。

> 加购实测把预警能力放大了一大截：以前「有货但不知道剩多少」的商品完全进不了预警，现在库存 1 件、2 件、4 件这种会直接被顶到最上面。实测样例：B0HFWLCSCS 亚马逊页面只写 `In Stock`，加购探针挖出**卖家可售 2 件**，立刻进了「自有商品·需处理」。

- 三个分组**都可以折叠**：标题本身就是按钮，带 `▾`（展开）/ `▸`（收起）箭头和条数，点一下收起那一组。折叠状态记在浏览器本地，刷新后保持；三组各自独立。
- 每个芯片都是**可点开的亚马逊链接**，悬浮能看到亚马逊页面原话（比如 `Currently unavailable.`）和本工具的判定依据。
- 芯片里有 `（上次「有货」）` 字样，说明这个状态是**新变的**——比一直就有的状态更值得看。
- **「有货，数量未显示」不列出来**：亚马逊本来就不给数字。**加了加购探针之后这种情况已经很少见**（云端 2026-09-25 那一跑是 0 个），因为探针把这些商品的数字挖出来了；只有探针也被拦（验证码）时才会残留。
- 右上角的 **低库存阈值**（默认 ≤10 件，可选 3/5/10/20/30/50）存在你自己浏览器里。数字调到 30，原本灰着的「仅剩 17 件」就会升级成重点。断货和无主报价**不受阈值影响**，永远列出。
- 底部还会提示当天有多少商品**采集异常 / 未采集**，并告诉你去「📋 当天数据」页筛选查看。

## 与其他版本的差别（如实说明）

- 具体库存数量：**能拿到了**，走加购实测探针（见上文）。库存列会区分口径：`仅剩 N 件`（亚马逊原话，页面或购物车）/ `库存 N 件`（亚马逊加购响应原话「the N available from the seller」）/ `≥ N 件` / `最多 N 件`（以上都是加购实测，带蓝色角标）/ `限购 N`（购买数量上限，**不是库存**）/ `有货`（确实没数字）/ `缺货` / `无主报价` / `未知`
- **能区分「单笔限购」和「实际库存」，而且不靠推断**：判据是亚马逊在加购响应里的**原话** —— `the N available from the seller`（＝库存）vs `limit N per customer`（＝限购）。这条思路源自卖家精灵（它的 `L` 标记 = Purchase Limit，官方说明其数据源是 `maxOrderQuantity` 且会**覆盖**库存计算）—— 但本工具不照搬它的 `maxOrderQuantity` 参数（那个字段不在静态 HTML 里），而是用可观测的原话。**早期那版「靠没打印 low-stock 文案反推限购」的做法已被用户实测证伪并删除**（详见上文）。
- 探针每天每个商品多花约 3 个请求（商品页 + 加购 + 读购物车 + 删条目）。28 个商品每天多约 100 次请求，仍在 GitHub Actions 免费额度内
- 网页是公开地址 + 口令门（防误入，非加密）。若介意，可改用私有仓库跑采集（每月 2000 分钟免费额度，本工具每天约 30 分钟，够用）
- GitHub Actions 的定时在高峰期可能延迟几分钟到十几分钟，属正常现象
